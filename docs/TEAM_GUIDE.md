## 1. Day 0 — 킥오프 (시작 전 반나절)

### 킥오프 미팅 1시간, 안건 4개만
1. **역할 배정**
   - A(노동)/B(주택)/C(소비자)/D(금융) — 금융이 법령 4개로 제일 무거움 → 데이터 경험 많은 사람에게
   - **공용 리더 1명** 지정 (rag.py 오너십 + 공용 파일 충돌 중재)
2. **API 신청**
   - 국가법령정보센터(open.law.go.kr → OPEN API 신청: **법령 목록 + 본문**) — 수동 승인 1~2일
   - 한 명 키(OC) 받아 팀 공유 → `.env` (이미 .gitignore에 포함)
3. **레포 셋업**
   - 이 골격 업로드 + Squash merge 설정. 브랜치/직접-push 규칙은 CLAUDE.md '브랜치 전략' 따름 (소규모 5개 미만·비공용은 dev 직접 push 허용, 그 외·공용은 PR)
   - pre-commit(ruff) 설정, GitHub Actions CI 활성화 (.github/workflows/ci.yml 동봉됨)
4. **전원 로컬 검증** — 4명 각자 클론 후:
   ```bash
   pip install -r requirements.txt
   python graph.py        # 3케이스 출력 확인
   python -m pytest tests/  # 21 passed 확인
   ```
   "내 환경에서 안 돌아요"를 Day1에 발견하면 늦다.

### Day 0 체크리스트
- [ ] 역할 4개 + 공용 리더 확정
- [ ] 국가법령정보센터 API 신청 완료 (승인 대기 시작)
- [ ] 레포 + 브랜치 규칙 + CI 동작 확인 (PR 하나 올려 pytest 자동 실행 확인)
- [ ] 4명 전원 로컬에서 graph.py + pytest 통과

## 3. Day 2~5 — 일일 리듬

### 아침 스탠드업 10분 (매일)
각자 3줄: 어제 한 것 / 오늘 할 것 / 막힌 것.
**공용 파일 작업은 여기서 선언** — "오늘 rag.py 제가 잡습니다" (동시 수정 충돌 방지)

### PR 규칙
먼저 **PR이 필요한지부터** (CLAUDE.md '브랜치 전략'): 5개 미만·비공용 변경은 `dev` 직접 push 허용(push 전 로컬 `pytest` 통과), 그 외/공용은 PR. PR일 때 승인 규칙:

| 대상 | 승인 | 비고 |
|---|---|---|
| 자기 분야 파일 (agents/<분야>.py) | 리뷰 1명 | 가볍게, 빨리 |
| 공용 파일 (state/graph/rag/contacts/drafter/supervisor/planner) | **전원 승인** | 개수 무관 항상 PR. SPEC 영향 시 SPEC PR 먼저 |
| 공통 | CI(pytest) 통과 필수 | 통과 없이 머지 금지 |

### 저녁 통합 체크포인트 (전원, 짧게)
- **Day 2 저녁**: 진짜 검색(벡터DB)으로 그래프 1회 관통 + **LangSmith 트레이싱 켜짐 확인**(smith.langchain.com에서 트레이스 보이는지)
- **Day 3 저녁**: 최소 1개 분야가 Bedrock 실답변 생성
- **Day 4 저녁**: 4분야 전부 Bedrock 답변 E2E + 문서초안 1개 동작 + 웹화면·Streamlit 실데이터 표시 확인(⑥)
- **Day 5 저녁**: 평가 수치 확보 — evals/results/ 이력에서 "단순검색 vs 하이브리드 hit@k" + "비용 절감률" 비교표 추출 (발표 자료의 핵심)

이 네 번의 "다같이 돌려보기"가 통합 지옥을 막는다.

### 매일 오후: 3축 측정 (Day3부터)
각자 `python scripts/evaluate.py <분야>` 1회 이상 — 평가(hit@k)/비용($)/환각(grounding) 확인.
숫자가 어제보다 나빠졌으면 그 변경은 롤백 후보. 이력은 자동 누적(evals/results/).

### 손이 빈 사람
자기 분야 끝나면 TODO.md의 [공용] 항목을 **위에서부터** 가져간다.
가져갈 때 스탠드업이나 채널에 선언 → 중복 작업 방지.
