# HARNESS.md — 이 프로젝트의 하네스 엔지니어링

> 하네스 엔지니어링(Harness Engineering): 모델 자체가 아니라 **모델을 감싸는 구조**
> (도구, 검증, 피드백 루프, 계약)를 설계하는 것. 핵심 사상 한 줄 —
> **"에이전트가 실수했을 때, 같은 실수가 구조적으로 재발 불가능하게 만든다."**
> 프롬프트로 '부탁'하지 않고, 구조로 '강제'한다.
> (2026.2 Mitchell Hashimoto가 명명, OpenAI "Harness engineering" 글로 확산)

이 프로젝트는 두 층위에서 하네스를 적용한다:
- **A. 제품 하네스** — 우리 서비스(법률 상담 에이전트)를 감싸는 구조
- **B. 개발 하네스** — 우리가 Claude Code 등으로 개발할 때 에이전트를 감싸는 구조

---

## A. 제품 하네스 — 서비스가 환각할 수 없게 만드는 구조

### A-1. Verifier 노드: 환각의 도달 경로 차단 ★핵심★

**문제**: "검색된 조문만 근거로 답하세요"라는 프롬프트는 부탁이다. 모델은 가끔 어긴다.
**하네스**: 부탁을 검증 레이어로 바꾼다.

```
                     ┌─ labor ──┐
질문 → supervisor ──┼─ housing ─┼─→ [verifier] ─→ planner → 사용자
                     ├─ consumer┤      │
                     └─ finance ┘      └─ 근거 없는 답변은 여기서 탈락
                                          (사용자에게 도달할 경로 자체가 없음)
```

동작 (`agents/verifier.py`):
1. 각 전문가의 답변에 대해 `_is_grounded(answer, citations)` 검사
   - 인용 조문이 없거나 / 조문 원문(snippet)이 비었거나 / confidence < 0.5 → **탈락**
   - Day4 실제 구현: 어휘 겹침 검사 → Bedrock "주장-조문 근거 판정"의 2단계
2. 통과분만 `verified_answers`에 담아 Planner로
3. Planner는 `verified_answers`**만** 사용 — 검증 안 된 답변은 코드 경로상 사용자에게 갈 수 없다
4. 전부 탈락하면? 지어내지 않고 정직하게 "근거가 충분하지 않다" + 상담 연락처
5. `verification_report`에 탈락 내역 기록 → "환각 차단 N건"이 발표 지표가 됨

**테스트로 보증**: `test_verifier_drops_uncited`(인용 없으면 탈락),
`test_planner_honest_when_all_dropped`(전부 탈락 시 정직 거절) — CI에서 매 PR 검증.

### A-2. contacts.py: 신뢰 필수 출력을 모델 밖으로

전화번호·기관명은 하나만 틀려도 신뢰가 무너진다.
→ LLM이 생성하는 것 자체를 금지하고, 검증된 하드코딩 데이터(`common/contacts.py`)에서만 가져온다.
**환각 확률 0이 아니라, 환각이 불가능한 구조.** 가장 교과서적인 하네스 패턴 —
"모델이 잘하길 바라지 말고, 모델이 못 망치게 설계하라."

### A-3. llm.py: 구조화 출력 강제 + 재시도 루프

모델에게 "JSON으로 답해줘"는 부탁이다. `common/llm.py`의 `call_bedrock_json()`은:
1. JSON-only 지시 + 필수 키 명시
2. 파싱 실패/키 누락 시 **오류 내용을 알려주며 자동 재시도** (피드백 루프)
3. 재시도 소진 시 예외 → 호출자가 안전 폴백 (그 답변은 verifier에서 탈락)
형식 위반이 후속 코드에 도달하는 것을 구조적으로 차단한다.

### A-4. 코드 레벨 경계 (모델 판단에 안 맡기는 것들)

| 경계 | 구현 | 왜 하네스인가 |
|---|---|---|
| 범위 밖 거절 | supervisor `route()` → 4분야 아니면 planner 직행(거절) | 형사 등 못 다루는 질문에 모델이 '시도'할 기회 자체를 제거 |
| 면책 문구 | planner가 코드로 항상 삽입 | 모델이 빼먹을 수 없음 |
| 문서 초안 '초안' 표시 | drafter가 guide에 코드로 강제 | "완성 법률문서"로 오인될 경로 차단 |
| RAG 컨텍스트 제약 | 프롬프트에 검색 조문만 주입 + verifier 이중 방어 | 1차(컨텍스트 제한) + 2차(검증) 겹층 방어 |

## B. 개발 하네스 — 4명의 AI 에이전트가 사고 못 치게

### B-1. CLAUDE.md = AGENTS.md 패턴
Claude Code가 매 세션 자동으로 읽는 행동 규약. "신입 팀원 온보딩 문서"처럼
스택 버전, 파일 소유권, 금지 사항을 명시 → 4명의 에이전트가 같은 규약으로 작동.

### B-2. 실수 축적 루프 (Hashimoto 패턴) ★운영 규칙★
CLAUDE.md의 "자주 하는 실수" 섹션은 **살아있는 문서**다.
> **규칙: 6일 동안 누구의 Claude든 실수를 하면, 고치고 끝내지 말고
> 그 실수를 방지하는 한 줄을 CLAUDE.md에 추가하는 PR을 같이 올린다.**
"다음부터 잘해"가 아니라 구조적 재발 방지. 비용 0, 효과 누적.

### B-3. 계약 테스트 + CI = 강제되는 피드백 루프
SPEC.md(계약) → test_contracts.py(코드화) → GitHub Actions(매 PR 자동 실행).
에이전트가 계약을 어긴 코드를 짜면 **머지 자체가 안 된다.**
사람이 눈으로 잡는 게 아니라 구조가 잡는다.

### B-4. 파일 소유권 + 공용 파일 전원 승인
한 에이전트의 수정 범위를 구조로 제한 → 충돌과 오염을 머지 규칙이 차단.
- **변경 규모로 게이트 차등**(CLAUDE.md 브랜치 전략): 5개 미만·비공용은 `dev` 직접 push(로컬 pytest 통과 조건), 5개 이상·공용은 PR. 공용 파일은 개수 무관 항상 PR+전원 승인 → 모두 막히는 파일을 리뷰 없이 못 바꾸게 구조로 강제.
- **CLAUDE.md 계층 분리**(공통/개인): 팀 규약(CLAUDE.md, 커밋)과 개인 메모(CLAUDE.local.md, gitignore)를 분리 → 개인 컨텍스트가 공통 규약을 오염시키지 않음.

### B-5. Conventional Commits + 브랜치 네이밍 규약
`<type>(<scope>): 제목` 커밋 + `<type>/<scope>-주제` 브랜치 → 4명의 에이전트가 동일한 형식으로 이력을 남겨, 변경 추적과 리뷰 단위가 구조적으로 일관됨.

## 요약: 부탁 vs 하네스

| 부탁 (프롬프트) | 하네스 (구조) |
|---|---|
| "조문만 근거로 답해줘" | verifier가 검사, 탈락분은 도달 경로 없음 |
| "전화번호 정확히 써줘" | LLM 생성 금지, contacts.py에서만 |
| "JSON으로 답해줘" | 파싱 실패 시 자동 재시도, 소진 시 탈락 |
| "면책 문구 넣어줘" | planner가 코드로 항상 삽입 |
| "계약 지켜서 짜줘" | 계약 테스트 + CI, 위반 시 머지 불가 |
| "다음부턴 그 실수 하지 마" | CLAUDE.md에 방지 규칙 축적 |

## 발표/면접 멘트
"환각 방지를 프롬프트로 하지 않았습니다. 연락처는 모델 밖 검증 데이터에서만 오고,
모든 답변은 인용-근거 검증 노드를 통과해야만 사용자에게 도달하며,
팀의 코드 계약은 CI가 강제합니다 — 모델에게 부탁하는 대신,
실수가 구조적으로 불가능한 하네스를 설계했습니다."
